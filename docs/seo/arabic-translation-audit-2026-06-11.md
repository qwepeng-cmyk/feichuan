# N-TET Arabic Translation Audit

Date: 2026-06-11
Scope: `/ar` public site copy across `src/dictionaries/ar.json`, SQLite `_ar` fields, hardcoded home/category/SEO copy, and representative visible pages.

## Executive Summary

The Arabic version is structurally live, but the translation quality is not publication-ready for a serious Arabic-market launch.

The current Arabic content was generated by a term-replacement workflow rather than full translation. Many records combine English sentence structure with isolated Arabic technical terms, producing visible mixed-language copy such as `Stationary RF كشف نظام`, `Airport أمن Protection`, and long English paragraphs with a few Arabic substitutions.

This is a quality and conversion risk, not a routing or build risk. The `/ar` pages render, sitemap/llms outputs include Arabic URLs, and RTL initialization exists, but the copy should be treated as machine draft only.

## Audit Method

- Parsed `src/dictionaries/ar.json` and compared leaves against `src/dictionaries/en.json`.
- Queried published SQLite records in `products`, `solutions`, `cases`, and `media`.
- Checked `_ar` fields for empty content, exact English carryover, high Latin-word ratio, awkward Arabic-English word order, and visible English operational terms.
- Sampled rendered local pages for `/ar`, `/ar/products`, product detail, `/ar/solutions`, solution detail, `/ar/cases`, `/ar/media`, and `/ar/contact`.
- Reviewed the generation script `scripts/sync-arabic-locale.py` to identify root cause.

## Findings

### P0 - Arabic copy is mostly not real Arabic translation

Programmatic scan results:

- Total audited text records: 1,428
- Records with notable translation issues: 1,087
- Severe issue records: 986

Affected surfaces:

- `products`: 736 issue records
- `solutions`: 137 issue records
- `dictionary`: 148 issue records
- `cases`: 51 issue records
- `media`: 12 issue records
- hardcoded Arabic snippets: 3 issue records

The issue is systemic. It affects page titles, card labels, summaries, detail pages, form UI, product specs, case descriptions, and media content.

### P0 - Product and solution detail pages have highly visible mixed-language titles

Examples:

- English: `Stationary RF Detection System`
- Current Arabic: `Stationary RF كشف نظام`

- English: `Airport Security Protection`
- Current Arabic: `Airport أمن Protection`

These are prominent H1/title-level strings, so they are likely to be noticed immediately by Arabic readers.

### P0 - Long DB fields preserve English sentence structure

Example from product summary:

Current Arabic draft begins with:

`Stationary RF كشف نظام يدعم The RF كشف نظام monitors radio signals emitted by طائرات بدون طيار...`

Example from solution summary:

`Airport أمن Protection يدعم An integrated airport أمن solution for terminal entrances...`

These are not acceptable Arabic marketing or technical copy. They are English paragraphs with term substitutions.

### P1 - Dictionary UI still has exact English carryover

Examples found in `src/dictionaries/ar.json`:

- `common.learnMore`: `Learn More`
- `common.product`: `Product`
- `common.backToTop`: `Back to Top`
- `inquiry.subtitle`: full English paragraph
- `inquiry.submitted.subtitle`: full English paragraph
- many country and region options remain English
- multiple `megaMenu.*` entries remain English

Some brand names and acronyms can remain Latin, but UI commands and form instructions should be Arabic.

### P1 - Case pages have weak or untranslated operational copy

Case pages show mixed-language descriptions and titles, for example:

- `Airspace Monitoring Case of a Refinery in Brazil`
- Current Arabic: `المجال الجوي مراقبة Case of a Refinery in Brazil`

Country fields also include machine-prefix artifacts such as `نظام Brazil`.

### P1 - Media/articles are not ready for Arabic SEO

Media content exists in `_ar`, but it contains the same term-replacement pattern. Arabic article pages may render, but they are not useful enough for Arabic organic search, citation, or buyer trust.

### P2 - RTL implementation is functionally present, but raw root HTML still starts as English

Representative `/ar` pages include a locale initialization script that sets:

- `document.documentElement.lang = "ar"`
- `document.documentElement.dir = "rtl"`
- `document.documentElement.dataset.locale = "ar"`

However, the root static HTML still starts with `lang="en"` because the root app layout owns the `<html>` tag. Browser rendering is corrected by the locale layout script, but this is not as clean as server-emitted `lang="ar" dir="rtl"`.

This is lower priority than translation quality, but worth fixing later if Arabic SEO becomes important.

## Root Cause

`scripts/sync-arabic-locale.py` is a term-map generator, not a translation workflow. It uses exact phrase replacements and regex term substitutions, then wraps the result with Arabic boilerplate. This explains:

- mixed English-Arabic titles
- English word order
- long English paragraphs with isolated Arabic substitutions
- inconsistent handling of technical terminology
- untranslated dictionary leaves

The script is useful for schema coverage, but not for publication-grade Arabic.

## Recommended Remediation

### Phase 1 - Blocker Fix Before Launch

Replace generated Arabic content for the most visible surfaces:

- `src/dictionaries/ar.json`: navigation, header mega menu, footer, inquiry form, contact, product/solution/case/media labels
- homepage hardcoded copy in `src/constants/homeData.ts`
- solution category landing copy in `src/lib/categoryLandingData.ts`
- core SEO metadata in `src/lib/seoMetadata.ts`
- top product and solution detail titles/summaries in `data/ntet.db`

Suggested priority pages:

- `/ar`
- `/ar/products`
- `/ar/products/stationary-rf-detection-system`
- `/ar/solutions`
- `/ar/solutions/airport-security-protection`
- `/ar/cases`
- `/ar/media`
- `/ar/contact`

### Phase 2 - Batch Re-Translation

Replace the current sync script with a true translation pass:

- translate full strings, not isolated terms
- preserve approved terms such as `N-TET`, `UAV`, `RF`, model names, units, and product handles
- keep compliance boundaries from English source
- write `_ar` fields and `raw_json` together
- generate a QA report after writing

### Phase 3 - Human Editorial Pass

After batch translation, manually review:

- homepage hero and CTAs
- product category labels
- top 10 product detail pages
- top 8 solution pages
- contact/inquiry form
- SEO titles and descriptions

Use Modern Standard Arabic for public site copy. Keep technical acronyms where Arabic buyers expect them, but translate surrounding syntax naturally.

## QA Gates For The Fix

Run these after retranslation:

- Arabic text coverage: no empty `_ar` fields for published records
- English carryover: no exact English copy except brands, model names, acronyms, units, and intentional country names
- Latin ratio check: flag visible strings where Latin words dominate the Arabic sentence
- `raw_json` parity: `_ar` table fields match `raw_json`
- `npm run build`
- `npm run generate:llms`
- `npm run audit:public-risk`
- local page check for `/ar` core pages

## Publication Recommendation

Do not treat the current `/ar` version as launch-ready. It is acceptable as an internal technical preview proving routing, RTL, database fields, sitemap, and rendering. It should not be promoted publicly until the visible Arabic copy is regenerated with sentence-level translation and reviewed on the top commercial pages.
